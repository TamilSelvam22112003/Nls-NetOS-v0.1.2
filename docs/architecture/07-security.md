# 07 — Security

Status: Draft v0.1.2. Algorithms, key usage and replay mechanisms are defined only in the NLS security specification; this document states ownership and policy and references them. Markers: **[Specified]**, **[Decision pending]**, **[Not implemented]**.

## 1. Security goals

Confidentiality and integrity of protected traffic, peer authentication through Router-CA trust, replay resistance, fail-closed behavior for traffic that requires NLS.

## 2. Distinct concepts

| Concept | Meaning |
|---|---|
| Identity | who a router claims to be |
| Authentication | proof of that claim (key possession) |
| Certificate validation | chain, validity, status |
| Trust decision | whether the identity is accepted as a peer |
| Authorization | which NLS operations it may perform |

A valid certificate does not authorize every operation.

## 3. Keys and ownership

| Key | Generated by | Stored by | Used by | Rotated or invalidated by |
|---|---|---|---|---|
| Router asymmetric key pair | router crypto subsystem at boot | key store or secure hardware | router (authentication, key agreement) | router, on renewal or compromise |
| Router symmetric key material | router crypto subsystem at boot | key store | router (use defined by ADR) | router |
| Router certificate | Router-CA | router (reference), CA registry | router, peers | Router-CA |
| Session keys | key agreement between routers | key store | data plane | session manager |
| CA signing key | Router-CA | CA key protection | Router-CA | CA operations |

Router-CA never holds router private keys or session keys. **[Decision pending]**: how a router's own symmetric key material relates to per-peer session keys. Recommendation: derive per-peer session keys from an authenticated key exchange and keep lifetimes short, rather than reusing one long-lived static symmetric key across peers.

## 4. VIP security

- VIP is a temporary identity generated with a SHA algorithm; hash variant and inputs per specification. Recommended: a current SHA-2 or SHA-3 family hash; weak variants such as SHA-1 are not acceptable **[Decision pending: ADR]**.
- A hash is not a secret and not authentication. VIP is never used alone to trust a peer; authentication relies on certificates and signatures.
- Inputs should include a fresh nonce and time bucket so a captured VIP cannot be reused; the specification fixes the exact inputs.
- A VIP expires once secured communication is established and after a bounded timeout if unused. Expired VIPs are rejected and not reused.
- Rate-limit VIP requests per source to resist exhaustion.

## 5. Router-CA trust

Trust anchors are provisioned out of band; none is accepted from an unauthenticated source. The CA connection is authenticated (for example mutual TLS) against the provisioned anchor; the approved transport and validation configuration is referenced here **[reference required]**. Anchor updates must be signed by an existing anchor.

### Logical interface

| Operation | Purpose | Auth | Router validates |
|---|---|---|---|
| Enroll | obtain certificate | bootstrap credential | chain, key match, validity |
| Renew | replace expiring certificate | current identity | same |
| Peer-info | peer certificate and status | router identity | signature, chain, status, freshness |
| Status | revocation check | router identity | signature, freshness |
| Trust update | anchors or policy | router identity | signature by existing anchor |
| Authorization policy | permitted operations | router identity | signature |

Message formats: **[reference required]**.

## 6. Router-CA unavailable

| Situation | Behaviour (**[Decision pending]** policy) |
|---|---|
| No valid identity at boot | cannot enroll, NLS not started |
| Valid cached identity | allowed only if policy permits within maximum cache age |
| During operation | existing sessions continue until expiry; no new peers unless cached trust valid and permitted |
| Expired certificate | renewal attempted; no new NLS operations |
| Stale revocation data | recommended fail closed for new sessions |
| Recovery | re-sync trust, status, policy; reconcile sessions |

## 7. Revocation effects

Adjacencies torn down, neighbor metadata and advertisements removed, VIPs and sessions invalidated, data plane stops NLS forwarding to and from the router, FIB updated through the normal path.

## 8. Replay, integrity, encryption

Encryption alone is not authentication and does not prevent replay. Authentication tag, sequence handling and replay window are required and are defined in the specification **[reference required]**. Use vetted AEAD ciphers and standard key agreement and signature algorithms; no custom primitives.

## 9. Threat summary (STRIDE)

| Threat | Example | Mitigation |
|---|---|---|
| Spoofing | forged VIP or NLS-OSPF packet | certificate-based authentication, trust validation |
| Tampering | modified LSA or secured packet | integrity tags, authenticated advertisements |
| Repudiation | denied key or route change | audit logging |
| Information disclosure | key leakage, plaintext leak | secure key store, no secrets in logs or tables, fail closed |
| Denial of service | VIP or adjacency flood | rate limiting, early cheap validation |
| Elevation of privilege | valid cert used beyond rights | separate authorization policy |

## 10. Logging

Never log private keys, symmetric secrets or full key material. Log identifiers and outcomes only.
